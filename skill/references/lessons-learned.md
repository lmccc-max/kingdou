# 金豆计件工资管理 - 历史教训

## [LRN-20260511-001] cron job 与主 agent 冲突导致重复记录
**问题**: 用户提交 `0.02 3` 后，飞书群内出现两条确认消息（编码 101 和 102），Bitable 中产生两条完全相同的待审核记录
**根因**: `piecework-cron-guard`（每分钟运行）从 `gateway.log` 独立 grep 最新消息并匹配纯数字格式，与主会话 agent 并行处理同一条消息。两条处理路径互不可见，各自提交一次。
**发现方法**: 
1. 查 Bitable 确认有两条记录 → `cronjob(action='list')` 发现 `piecework-cron-guard`
2. 读 cron 输出文件 `~/.hermes/cron/output/a142e60cfa2b/2026-05-11_00-47-00.md` → 确认它提交了编码 102
**修复**: cron job 已被移除。**每次处理计件消息前先 `cronjob(action='list')` 检查冲突**。
**清理重复记录**: 调用飞书 API DELETE 删除重复的 record_id。

## [LRN-20260511-002] feishu-send-message.py 发送后禁止额外对话输出
**问题**: agent 通过 `feishu-send-message.py` 发送确认到群后，又在对话中输出 "The confirmation has been sent..."，用户质问"为什么会有这一条"
**根因**: 零废话原则执行不彻底——飞书 API 已将确认发给群，对话中的额外文本对用户是冗余噪音
**规则**: 提交确认仅通过 `feishu-send-message.py` 发送。agent 自身回复为空或仅"已处理"。绝不重复已通过 API 发送的内容。

## [LRN-20260503-001] BOM编码导致配置合并失败
**问题**: 从飞书导出的 JSON 文件带有 UTF-8 BOM（`efbb bf`），使用 `execute_code` 沙箱中的 `json.loads()` 会报错 `JSONDecodeError: Expecting value: line 1 column 1`
**解决方案**: 
- 使用 `terminal` 工具执行 Python，以 `encoding='utf-8-sig'` 打开文件
- 或先 `lstrip('\ufeff')` 去除 BOM 再 json.loads
- 不要在 `execute_code` 沙箱中直接处理带 BOM 的 JSON 文件

## [LRN-20260503-002] 飞书多群消息接收排查路径
**问题**: 飞书机器人在计件群中被拉入但收不到消息
**排查步骤**:
1. 检查系统日志: `journalctl --user -u hermes-gateway.service` 搜索 `Unauthorized user`
2. 确认网关进程环境变量: `cat /proc/$(systemctl --user show hermes-gateway.service --property=MainPID --value)/environ | tr '\0' '\n' | grep FEISHU`
3. 关键环境变量:
   - `FEISHU_ALLOW_ALL_USERS=true` — 允许所有飞书用户发消息
   - `FEISHU_ALLOWED_USERS` — 白名单（同上为 true 时此配置不生效）
   - `FEISHU_GROUP_POLICY=open` — 允许群聊消息
4. 网关重启后新配置才生效（`systemctl --user restart hermes-gateway.service`）
5. 排查源码位置: `gateway/run.py` 中 `_is_user_authorized()` 方法（约 2846 行）


## [LRN-20260505-001] 时间戳单位错误导致日期解析失败
**问题**: 查询工资记录时出现 `ValueError: year 58308 is out of range` 错误
**原因**: 飞书 Bitable 的日期时间字段返回的是**毫秒级 Unix 时间戳**（如 `1777882736000`），而 Python 的 `datetime.fromtimestamp()` 期望秒级时间戳
**解决方案**: 
```python
ts_ms = int(date_time_val)  # 1777882736000
ts = ts_ms / 1000           # 1777882736.0
dt = datetime.fromtimestamp(ts)  # 正确日期
```
**参考**: 详见 `references/feishu-api-patterns.md` 第6节"时间戳处理"

## [LRN-20260505-003] 编码格式不一致导致查询失败
**问题**: 查询编码281-285时找不到记录，因为预设了 `RF2026050XXX` 格式
**原因**: 不同计件群的编码格式可能不同：
- 员工<01>计件群: `RF2026050281` (带RF前缀的AutoNumber)
- 员工<02>计件群: `001`, `002`, `281` 等纯数字格式
**解决方案**: 
1. 查询时不要预设编码格式，先获取所有记录再筛选
2. 使用字符串包含匹配而非精确匹配：`if "281" in code`
3. 每个群的编码格式由其Bitable表格的"编码"字段配置决定
**参考**: 详见 `references/api-data-parsing.md`

## [LRN-20260505-004] API返回字段格式陷阱
**问题**: 解析字段值时得到 `[{"text": "员工<02>", "type": "text"}]` 而不是预期的字符串
**原因**: 飞书Bitable的文本字段返回的是富文本数组格式，不是简单字符串
**解决方案**: 需要提取数组中的text值
```python
def parse_text_field(field_value):
    if isinstance(field_value, list) and len(field_value) > 0:
        if isinstance(field_value[0], dict) and 'text' in field_value[0]:
            return field_value[0]['text']
    return str(field_value) if field_value else ''
```
**参考**: 详见 `references/api-data-parsing.md` 完整解析指南

## [LRN-20260505-005] 会话 chat_id 与配置 chat_id 不匹配
**问题**: 会话上下文中的 chat_id (`oc_<redacted-05>`) 与配置文件中的 chat_id (`oc_<redacted-06>`) 不一致，导致找不到群配置
**原因**: 飞书会话的 chat_id 可能因会话重建、群迁移等原因发生变化，而配置文件使用固定的群 ID
**解决方案**: 
1. 通过 `HERMES_SESSION_KEY` 环境变量获取当前会话的 chat_id
2. 如果配置中找不到，检查 `FEISHU_HOME_CHANNEL` 环境变量作为备选
3. 查看配置文件中所有可用的群聊 ID，确认正确的映射关系
4. 必要时更新配置文件中的 chat_id 或建立新旧 ID 的映射表

## [LRN-20260505-006] execute_code 沙箱无法访问环境变量
**问题**: 在 `execute_code` 沙箱中使用 `os.environ.get('FEISHU_APP_ID')` 返回 `None`
**原因**: Python 沙箱环境与 shell 环境隔离，无法直接访问系统环境变量
**解决方案**: 
```python
import subprocess
# 方法1: 使用 subprocess 读取环境变量
result = subprocess.run(['bash', '-c', 'echo $FEISHU_APP_ID'], capture_output=True, text=True)
app_id = result.stdout.strip()

# 方法2: 使用 terminal 工具执行 Python 脚本
# 在 terminal 中直接运行 python3 命令可以访问完整环境
```
**建议**: 对于需要环境变量的飞书 API 调用，优先使用 `terminal` 工具执行 Python 脚本

## [LRN-20260507-001] 用户反馈记录存在但API查询不到
**问题**: 用户明确告知编码307记录存在（并提供之前的确认回复作为证据），但API查询返回编码范围仅到306，找不到307
**原因分析**:
1. API查询可能存在缓存延迟，新创建的记录不会立即出现在查询结果中
2. 用户提供的确认回复证明记录确实已被创建（系统分配了编码307）
3. 我过于相信API查询结果，没有充分考虑用户提供的证据
**解决方案**:
1. **信任用户证据**: 当用户明确告知记录存在并提供证据时，应优先信任用户而非完全依赖API查询
2. **重试机制**: 对于刚创建的记录，API查询可能需要几秒到几分钟才能同步，应增加重试或延迟查询
3. **直接操作**: 如果用户提供了编码，可以直接尝试更新操作，即使查询不到也执行（飞书API允许直接通过record_id或条件更新）
4. **承认错误**: 当用户指出错误时，立即承认并重新核实，而不是坚持API查询结果

**教训**: 用户提供的确认回复是系统生成的权威证据，比API查询更可靠。当两者冲突时，应优先采信用户证据并尝试直接操作。

## [LRN-20260507-002] 响应速度要求 - "快点的"
**问题**: 用户多次催促"快点的"，表明对响应速度不满意
**原因**: 在查询记录时过于谨慎，多次确认，导致响应延迟
**解决方案**:
1. **快速响应优先**: 收到指令后快速执行，减少中间确认步骤
2. **边执行边验证**: 不要等待完整验证后再回复，可以先执行再验证
3. **用户催促时加速**: 当用户明确催促时，跳过非关键验证步骤直接执行

## [LRN-20260507-003] 细心程度要求 - "为什么不细心"
**问题**: 用户质问"为什么不细心"，指出在查询307记录时不够仔细
**原因**: 过于依赖API查询结果，没有充分考虑用户提供的证据（之前的确认回复）
**解决方案**:
1. **综合判断**: 不要仅依赖单一数据源（API），要结合用户提供的所有信息
2. **重视用户反馈**: 当用户指出记录存在时，应深入排查而非简单重复查询
3. **承认错误及时**: 发现错误后立即承认并修正，不要辩解

## [LRN-20260507-004] 数量修正指令不明确导致混淆
**问题**: 用户说"记录的数量出错了"并回复"105"，不清楚是指哪个编码需要修改为105
**场景**: 
- 编码265: 108件（待审核）
- 编码266: 105件（待审核）
- 用户说"105"可能是指：
  1. 编码265改为105件
  2. 确认编码266的105件正确
  3. 两个都要修改
**解决方案**:
1. **明确询问**: 收到模糊的数量修正指令时，必须明确询问"请问是要修改编码X的数量为Y件吗？"
2. **列出选项**: 列出当前待审核的所有记录，让用户指明具体要修改哪个
3. **确认后再执行**: 不要假设用户意图，确认清楚后再执行修改

**示例对话**:
- ❌ 错误做法: 直接猜测用户意图并执行
- ✅ 正确做法: "当前待审核记录：\n编码265: 108件\n编码266: 105件\n请问您是要修改编码265为105件吗？"

## [LRN-20260507-005] 审核人填写规则错误（2026-05-07最终版）
**问题**: 在审核通过/拒绝时，我固定填写了"管理员"作为审核人，而不是从中央配置文件的`openid_name_mapping`中查询实际发送消息的用户姓名
**原因**: 未正确执行审核人填写规则，使用了固定值而非动态查询
**正确流程**:
1. 从会话获取发送者OpenID（`sender_id`或`user_id`）
2. 查中央配置文件`~/.hermes/skills/kingdou/configs/piecework-groups.json`中的`openid_name_mapping`
3. 使用映射的姓名填入审核人字段
4. 如果OpenID在映射表中找不到，询问用户"请问您的姓名是？"或留空

**禁止行为**:
- ❌ 禁止固定填写默认审核人（如"管理员"、"管理员<01>"、"管理员<03>"等）
- ❌ 禁止从消息内容中解析"审核人"字段（可能不正确）
- ❌ 禁止猜测审核人身份

**示例**:
- 管理员<03>(OpenID ou_<redacted-03>)发送消息→查映射表得"管理员<03>"→审核人填"管理员<03>"（即使消息内容显示"审核人：管理员<01>"）

## 防错机制总结

1. **绝不跳过预加载**: 每次处理计件消息都必须重新加载配置
2. **不凭印象工作**: 所有参数都从预加载的配置文件中读取  
3. **实时同步**: 配置变更会在下次预加载时立即生效
4. **本地完成**: 预加载只读取本地文件，不消耗API Token
5. **双重验证**: 关键操作必须进行前后验证
6. **信息隔离**: 严格执行跨群数据隔离原则
7. **环境变量备选**: execute_code 沙箱无法访问环境变量时，使用 terminal 工具执行
8. **信任用户证据**: 当用户提供系统生成的确认回复作为证据时，优先信任用户而非完全依赖API查询
9. **快速响应**: 收到指令后快速执行，减少不必要的中间确认
10. **细心核查**: 综合所有信息源进行判断，不遗漏用户提供的证据
11. **审核人动态查询**: 必须通过OpenID查`openid_name_mapping`获取真实姓名，禁止固定填写

**问题**: 提交计件后未立即创建和返回编码，用户多次提醒"为什么不直接创建编码"
